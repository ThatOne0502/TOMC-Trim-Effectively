# TOMC-Trim Effectively 设计理念

> 写给设计者之间对话用：这份文档只谈取舍，不谈代码。
> 读完你能知道每个决定在防什么、放弃了什么、以及哪些东西是有意不做而不是还没做。
> 机制细节在 [实现原理](INTERNALS.md)，字段与数值在 [数据文档](DATA.md)，玩家视角在 [内容说明](CONTENT.md)。

口径：1.21.11 / Fabric / 单人向为主、联机可用；模组不改任何原版纹饰的获取与外观，只往「纹饰已经存在」这件事上加语义。

---

## 1. 三条线

整个项目可以压成三句话：

1. **内容在数据里，判断在引擎里。** JSON 说「哪条纹饰给什么」，代码说「怎么数、怎么算、什么时候触发」。加内容不需要编译，改引擎不需要碰数据。
2. **代码不认「第几级」，只认「几件」。** 纹饰不是附魔，没有等级、没有经验值、没有升级路线。
3. **客户端只做表现。** 所有数值在服务端算完；客户端拿注册表算 tooltip、画声音标注。这决定了下一条：客户端看到的东西不能在服务端构成事实，反过来也一样。

后面每一条都在解释这三句话为什么这么写，以及代价。

---

## 2. 为什么按件数，不按等级

原版给了我们一个天然的计量单位：**带同一套纹饰的部件个数**。四件盔甲，最多四件；加上主手副手，最多六件。

选它的理由，按重要性排：

- **可预期。** 全钻石套的哨垒是 4 件，摘掉胸甲就是 3 件。玩家穿脱时能自己算出来，不需要打开界面看数值。
- **不引入新的进度系统。** 等级需要一个「怎么涨」的答案（挖矿？战斗？挂机？）。任何答案都会变成一条新的 grind 线，而这个模组不打算发这个牌。
- **上限自然存在。** 六件封顶，所有效果都自带上限，省掉一整类平衡问题。
- **与「材料」正交。** 同一件装备上，纹饰给一套效果、材料给另一套，各自按自己的件数算。18 种纹饰 × 11 种材料不需要交互表。

代价也必须写清楚：

- **四件套是最优解。** 想要效果就得**穿满**，这会把玩家的搭配自由推向「一整套同纹饰」。这是设计接受的：纹饰在生存里本来就靠模板稀缺，凑齐一套本身就是目标。
- **没有成长曲线。** 从第一件到第四件是线性的，没有质变点。补偿方式是把数值放在「玩家能控制的变量」上（距离、速度、残血、金组数、有害效果数），让同一套衣服在不同处境下有不同表现。
- **与附魔是纯乘法叠加。** 我们不打算压附魔，也不打算为附魔让路；四件套 + 保护 IV 是强的，这是承认的。

`stack` 的四种叠法（`per_piece` / `per_piece_capped` / `once` / `full_set`）是为了让「按件数」这条主线能容纳少数例外，而不是为了造四套体系。实际数据里只有 `per_piece`、`once`、`full_set` 三种在用；`per_piece_capped` 留在契约里没有实现。

`iron` 那条是唯一一处「故意不用 per_piece」：它的数值作用在 `armor` 上，而 `per` 已经取了`gear.armor`（四件护甲值之和）。再乘一次件数就是把同一件算两遍，所以写 `once`。这不是平衡选择，是防止重复计数。

## 3. 为什么纹饰身份要盖章

盖的是三件事：这套盖章值是**哪条纹饰 + 哪个材料**算出来的；它给物品加了哪些属性；这件物品的效果是不是被关掉了。

要盖章而不是「每次需要的时候现算」，是因为三处硬约束：

- **物品比穿戴者活得久。** 展示框里的胸甲、掉落物、被别的模组翻过的背包，都没有穿戴者可以拿来做上下文。要看「这件东西有什么效果」，只能看它自己身上写着什么。
- **10 tick 一次的引擎不能每次重写物品。** 无条件重算会让组件版本每轮变一次，客户端跟着重绘 tooltip；顺带把玩家在铁砧或创造模式里手写过的同名属性抹掉。
- **盖章只写一次，就能被离线读到。** 对 `reconcile` 的设计就是这样：值没变就什么都不做，连组件都不写。

代价是**旧物品不会自动升级**。数据包改了公式，已经躺在箱子里的那件还是老值。补法是三处：引擎每 tick 只扫一名玩家背包里一个槽位、打开物品栏时的物品 hook、以及 `/tre reload` 强制重刷。世界里没人碰过的容器不扫——一个物品只有经过玩家手上的时候才值得被采纳，这条是刻意的，不是遗漏。

第二条代价：`reconcile` 必须在「纹饰组件出现之前就存在」的物品上也成立。早年版本的装备没有章，第一次被扫到时要补一个**空章**——即使数据没给任何属性。否则「有纹饰、没章」既是合法状态又是待修的漂移，巡检永远修不完。

## 4. 为什么客户端只做表现

因为「客户端能算」和「客户端该算」是两件事。

模型上，客户端的输入来源是数据包同步下来的注册表 + 玩家自己的实体状态。用它算 tooltip、算标注、算渐隐，输入全齐；用它算伤害，输入不齐（拿不到服务端的随机数、拿不到别的实体的完整状态、也不该信任）。

所以分工是：**服务端是唯一的数值来源，客户端只做「怎么看」**。

两处落得比较深的：

- **幽匿标注**（`ward`）不做成服务端实体或数据包广播，而是客户端本地 spawn 一个 `TextDisplay`，只在本客户端可见、跟随光线、可透视、渐隐。理由不止「省同步」：1.21.9+ 的自定义世界空间渲染要接 submit 体系，成本远高于本地实体。代价是这条标注无法被服务端审计，也不进录像——接受。
- **tooltip** 是原位替换，不是新增行。一行换一行，键没按下时与原版完全一致。

代价清单：维护两套代码路径（声音与粒子）、客户端越界就退化成「看不见」、以及所有「客户端看起来对但服务端没发生」的 bug 都更难复现。

## 5. 为什么数据驱动，不写死

写死 29 条效果意味着：换一条效果改一次编译、做一次兼容；整合包想删掉某条效果只能整份 fork。

数据驱动换到的东西：

- **覆盖语义免费。** 同 id 后加载者胜，整份替换。想做「这条纹饰太强了」的人只需要放一个同名 JSON，不需要改代码。
- **扩展不需要我们动代码。** 别的模组加自己的纹饰，只要往同名目录里放数据，或者在自己的数据包里放一条 `pattern` 指向它——引擎不需要知道有这个模组存在。
- **数值调平衡是编辑文本。**

代价：

- **校验成了运行时的事。** JSON 写坏了不会编译报错，只会在本轮日志里打一次错，然后这条数据不生效。我们选择了「脏数据不生效 + 日志可查」而不是「加载失败」——一个坏文件不该让整个数据包废掉。
- **断崖更陡。** 所有调用都建立在「每轮重建索引」上，没有热路径缓存可以依赖。

## 6. 有意不做的三件事

### 不做表达式语言

`Value` 永远是 `value × Π per × 件数因子`，加上可选的 `power` 和 `min`/`max`。没有条件分支、没有函数、没有别的数据源。

理由：一旦允许写表达式，就要写解析器、要写沙箱、要回答「这个变量在客户端有没有值」、要处理表达式里的除零。而这个 mod 的乐趣不在「能写多复杂的效果」，在「把简单的东西凑成一组」——`power` 已经够表达「距离越远越强但变平」这种曲线，实测素材够用。

代价：像「残血时按比例加速并且有上限、同时随件数增加」这种组合，需要拆成两条数据。能接受。

同理没做的：`effect_id`（同一条效果在同一物品上出现两次时的区分）、条件 DSL（直接用原版谓词就够）、等级。

### 不做修饰符监测体系

早期方案是「监听属性变化、维护一张外部表」。放弃了，理由是它会跟原版和其它模组抢同一个事实：属性修饰符本来就是幂等的，同 id 覆盖。于是改成「每个（属性，条目）一个聚合修饰符，id 带前缀，重算前先摘自己的」。

判据写死在代码评审里：**任何需要遍历实体修饰符列表来判断的逻辑都是设计错误。** 换装、重登、死亡、卸载四种生命周期已经用前缀清理覆盖完。

### 不设减伤天花板

`damage_in` 是纯乘算通道，我们**不额外加一道「最多减 80%」的闸**——原版自己已经有上限，我们在它上面再叠一层会变成双重钳制，让数据作者算不清最终值。

保留的两道闸是原版语义，不是我们发明的：`#minecraft:bypasses_effects` 与 `#minecraft:bypasses_resistance` 标记的伤害（虚空、`/kill`、饥饿这类）直接跳过纹饰减伤。没有这两道，一个满减伤的玩家会连虚空都免疫。

取舍的代价：**纹饰减伤可以叠到很接近免疫。** 我们接受，因为它需要四件套 + 高移动速度（`spire` 是「每件每 1 m/s 减 1%」），跑起来才有减免，站桩没有；而且它是「进伤害计算的减伤」，不是无敌。

## 7. 为什么不拦截原版药箭的 1/8

原版对药箭的处理是**把药水效果除以 8**（时长与等级都缩），这是「箭比瓶弱」这条规则的唯一实现处。

我们选择**不干预**，也就是纹饰触发的 Endphase 走箭时只有 1/8 的时长，而不是我们按 `√(2×伤害)` 重新算。

三个理由：

1. **规则一致性。** 玩家已经知道「箭上的药效是 1/8」。让纹饰的箭例外，等于要求玩家记住第二套规则。
2. **箭是廉价的。** 无限弓 + 药箭是很容易量产的组合。让它的解离强度等于近战，等于把 `eye` 的最优解变成「别打了，射」。
3. **不需要额外代码就能得到平衡。** 不写这段代码，1/8 自然发生，而且和原版完全一致。

代价：**`eye` 的远程路线被削得比近战狠。** 这是有意的，也写在内容文档里，不是隐藏机制。

## 8. Endphase 的三次改判

一个自定义负面效果，本身不复杂，但它把三处取舍集中暴露了。

**第一版：基础 10 / 延长 15 / 强化 5 秒。** 解离度 = 时长秒数 × (等级 + 1)，挂在最大生命上。

**发现的问题：** 强化档把「扣减速率 ×2」与时长直接相乘，一口药下去就可能把玩家压在 1 点生命上限；再叠上「每次受伤抬高解离度」，等于一瓶药就把人推进速死轨道。任何把时长直接换算成生命的设计，都会在强化档失控。

**第二次改判：三档 20 / 40 / 10 秒。** 普通 20×1 与增强 10×2 的总扣减都是 20，只有归零的节奏不同：普通是持续流血，增强是十秒内速死。这样「强化 = 更快」而不是「强化 = 更痛」，语义干净。

保留的直觉冲突：**延长版更疼但更慢，强化版更快但总额一样。** 熟悉「药水等级越高越强」的玩家会先以为强化版掉血更多。我们没有加提示去解释它，因为 tooltip 里的时长已经在说这件事。

**第三个决定：纹饰触发时上多少秒。** 固定值会让 `eye` 变成「随便蹭一下也永久解离」。最后取 `√(2 × 本次伤害)`，逐件累加、无上限。

- 平方根让高伤不至于一秒清空，也让轻击有一点意义（1 点伤害 → 1.41 秒）。
- 按件数累加、不设上限是有意的：这是这个 mod 里最强的单点爆发，四件套近战必中时理应致命。
- 代价是**反伤链上会出现很长的时长**：打一个满 `eye` 的目标，对方用高伤武器，时长会滚起来。接受，因为那是「你选择用重武器打末影化身」的后果。

**水伤与死亡消息**：遇水完全照抄末影人（每 tick 1 点、不被护甲减免、不因为伤害再抬解离度）；死亡消息不新建 `DeathMessageType`，只新建伤害类型 + 两条 lang 文案，因为原版的 `message_id` 机制本来就是为此存在的。

## 9. 边界与代价

### 生效对象

引擎挂在 `LivingEntity` 上，不写玩家分支。所以穿纹饰盔甲的僵尸、骷髅、盔甲架都会吃效果；交易、跳跃、配种这类玩家专属条目在逻辑上自然不触发。

代价：**给怪穿纹饰是给怪加强度**，包括 `eye` 这种会把你打死的。这是特性不是漏洞，但服主需要知道。

### 工具与红石

`trimmable_tools` 之类的模组把工具塞进 `#minecraft:trimmable_armor` 标签，工具就带上了原版 `minecraft:trim` 组件。我们不写任何兼容代码——`TrimSnapshot` 读的是「任何槽位上任何带 `TRIM` 的物品」，所以自动生效。

代价：`item_property` 类效果（耐久 ×2、保留修复成本）会跟着落到工具上。承认，且这就是兼容该模组的好处。

### 性能

10 tick 一次遍历所有实体做属性重算，成本与实体数量线性。单人无感，大型服务器是实打实的开销。没有做「只算附近玩家」的优化，理由是这样会让「遥测」消失——`/tre dump` 必须能看到任何实体的状态。

### 可观测性

`/tre dump` 只列**已经算出来的东西**：条目、件数、每个属性的聚合值。它不重算、不求值条件（条件标 `[conditions NOT evaluated yet: n]`）。这是取舍：命令不能改变状态，才不会出现「执行一次 dump 之后数值变了」。

### 兼容风险

- 与任何也改属性修饰符的模组共存时，前缀是我们唯一的边界。别人也往 `trimeffectively:` 前缀里写 id 会冲突（概率极低）。
- 与 `Player#actuallyHurt` 的其它注入共存时，顺序取决于 mixin 优先级。我们选了默认优先级 + 在 TAIL 里结算，尽量不跟别人抢 HEAD。
- 数据包改版不追溯：改了公式，世界里的旧物品保持旧值，直到被扫到或 `/tre reload`。这是「盖章」的直接代价，见 §3。

---

## 10. 一句话收尾

这个模组不是「给盔甲加附魔」，是**给纹饰一个身份**：一套已经存在、靠模板稀缺、玩家会为了好看去凑的东西，加上「凑齐了会怎样」这一层。

所有取舍都围绕这一点：让人愿意穿同一套，而不是算哪套数值最高。
